# Diplom_2: API-тесты Stellar Burgers

Автотесты пяти эндпоинтов по [документации API](https://code.s3.yandex.net/qa-automation-engineer/python-full/diploma/api-Stelar_Burger_10.25.pdf?etag=3584917d935c90b69cb3ffaff58d4f34): регистрация, вход, изменение профиля, создание заказа и получение заказов пользователя.

## Запуск

Создайте виртуальное окружение, установите зависимости из `requirements.txt` и выполните:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest
```

Результаты Allure записываются в `allure-results/latest/`. Перед каждым запуском очищается только этот каталог, поэтому результаты разных прогонов не смешиваются. Для просмотра результатов при установленной [Allure CLI 2](https://allurereport.org/docs/v2/install-for-linux/):

```bash
allure serve allure-results/latest
```

## Готовый Allure-отчёт

Отчёт последнего проверочного запуска находится в [reports/allure/index.html](reports/allure/index.html). Скачайте файл и откройте его в браузере: все данные включены в один HTML-файл, отдельный сервер не нужен. Отчёт хранится в Git вместе с тестами, поэтому попадёт в pull request после отправки ветки `develop2`.

Чтобы обновить отчёт после нового запуска тестов, выполните с Allure CLI 2 и Java 17 или новее:

```bash
allure generate allure-results/latest --single-file --clean -o reports/allure
```

Исходные результаты в `allure-results/` исключены из Git. Готовый отчёт в `reports/allure/` включён в репозиторий.

## Организация тестов

По умолчанию тесты обращаются к `https://qa-stellarburgers.education-services.ru`. При необходимости адрес можно изменить через переменную окружения `STELLAR_BURGERS_URL`. Для запуска нужен сетевой доступ к стенду; в некоторых окружениях может потребоваться VPN.

Тестовые пользователи создаются с уникальными адресами и удаляются фикстурой после теста, в том числе если регистрация без обязательного поля неожиданно прошла успешно и API вернул токен. API не предоставляет метода удаления заказов. Проверка получения заказов создаёт одного пользователя с одним заказом и сравнивает весь список номеров с ожидаемым: посторонние и повторяющиеся заказы приведут к падению теста.

В `tests/` находятся только тесты и фикстуры. Запросы к API собраны в `api_client.py`, ожидаемые сообщения об ошибках — в `data.py`, генерация уникальных данных — в `helpers.py`.

## Известный баг API

`TestOrderCreation.test_unauthorized_user_cannot_create_order` выявляет создание заказа без авторизации. По принятому требованию и описанию авторизации на странице 5 документации ожидается `401` с телом `{"success": false, "message": "You should be authorised"}`.

Для воспроизведения получите существующий `_id` через `GET /api/ingredients` и отправьте `POST /api/orders` с телом `{"ingredients": ["<существующий _id>"]}` без заголовка `Authorization`. Фактически сервер возвращает `200` и создаёт заказ. Тело ответа приложено к тесту в Allure.

Этот сценарий учитывается как баг API. Проверка сохраняет ожидаемый `401`; до исправления сервера результат запуска — `19 passed, 1 failed`.

## Неопределённое тело ответа при неверном хеше

На странице 1 документации для неверного хеша ингредиента указан статус `500 Internal Server Error`. Формат и содержимое тела ответа не заданы. Поэтому тест проверяет документированный код `500` и сохраняет фактическое тело в Allure; требования к HTML или определённому тексту ошибки не добавляются.

Критерий задания «проверяется тело и код ответа» для этого сценария нельзя полностью закрыть без уточнения спецификации: сохранение тела во вложении не заменяет проверку его содержимого. После согласования ожидаемого тела нужно добавить соответствующее сравнение в `test_order_with_invalid_ingredient_hash_is_rejected`.
